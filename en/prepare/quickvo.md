# quickvo Code Generator

sqltoy's POJO/VO classes do **not rely on runtime reflection guesswork**; they are generated by the **quickvo** tool, which connects to the database and produces annotated entity classes based on the table schema. This guarantees an exact correspondence between objects and tables, and gives you full property code-completion when writing SQL.

- Download (releases): https://gitee.com/sagacity/sagacity-quickvo/releases
- For a complete configuration example, see the quickvo configuration in the `tools` directory of the `sqltoy-quickstart` project.

## 1. How It Works

quickvo is an executable jar (`sagacity-quickvo.jar`) launched via `quickvo.bat` (Windows) or `quickvo.sh` (Linux/Mac):

```bat
:: core statement of quickvo.bat
java -cp ./libs/* org.sagacity.quickvo.QuickVOStart quickvo.xml
```

- Put the database driver jar into the `libs` directory; quickvo loads the driver automatically;
- quickvo reads `quickvo.xml`, connects to the database, and generates the VO/POJO classes using freemarker templates;
- When writing `quickvo.sh` on Linux/Mac, pay attention to path separators (backslash → forward slash).

## 2. Key quickvo.xml Configuration

> For the schema location of `quickvo.xml` and IDE completion setup, see the [XML Schema Guide](../config/xml_schemas.md).

`quickvo.xml` mainly consists of `property` (parameters), `datasource` (database connection), and `tasks/task` (generation tasks). The structure below is for standalone execution (for the full configuration when using the Maven plugin, see [quickvo-maven-plugin](quickvo_plugin.md)):

```xml
<?xml version="1.0" encoding="UTF-8"?>
<quickvo xmlns="http://www.sagframe.com/schema/quickvo">
    <!-- property: global parameters or a parameter file, referenced later via ${} -->
    <property file="src/main/resources/application.yml" />
    <property name="project.package" value="com.demo" />

    <!-- datasource: database connection (values can be written directly or referenced via ${} from property) -->
    <datasource name="demo" url="jdbc:mysql://localhost:3306/demo"
                driver="com.mysql.cj.jdbc.Driver" schema="demo"
                username="root" password="***" />

    <!-- tasks: dist output path; task matches tables with the include regex; entity generates pojo, vo generates dto/vo -->
    <tasks dist="src/main/java" encoding="UTF-8">
        <task datasource="demo" author="dev" include="^SQLTOY_\w+" active="true">
            <entity package="${project.package}.entity" substr="Sqltoy" name="#{subName}" lombok-chain="true" />
            <vo package="${project.package}.dto" substr="Sqltoy" name="#{subName}VO" lombok-chain="true" />
        </task>
    </tasks>

    <!-- also configurable: primary-key (primary key strategy), cascade (parent-child cascade), type-mapping (type mapping), swagger (v3/v2/false) -->
</quickvo>
```

Key configuration:

| Configuration | Description |
| --- | --- |
| `property` | Global parameters or a parameter file (`file` imports an external config; `name`/`value` define parameters) |
| `datasource` | Database connection; **for multi-instance databases always configure `schema` or `catalog` correctly** (see the notes below) |
| `tasks` / `task` | `dist` output path and `encoding` charset; `task` matches table names with the `include` regex and is toggled by `active`; multiple tasks may generate into different packages |
| `entity` / `vo` | Generate POJO and DTO/VO respectively; `package` is the target package, `substr` strips the table-name prefix, `name` is the class-name template (`#{subName}`), `lombok-chain` generates chained setters |
| `swagger` | Generate swagger annotations: `v3`/`v2`/`false` (do not generate) |
| `field.support.linked.set` | Switch: whether the set methods in generated VOs return the object itself (chainable) |
| `primary-key` | Primary key strategy for tables; identity-type keys need no configuration. quickvo sets the strategy automatically based on the primary key type/length: `bigint` → snowflake, 22-character → DefaultIdGenerator, 26-digit → NanoTimeIdGenerator |
| `cascade` | Cascade operation configuration: load cascade (e.g. load only valid child tables), update cascade (delete needs no configuration — child rows are removed directly via the primary/foreign key), and `orderBy` (ordering when loading child tables, e.g. `showIndex desc`) |
| `type-mapping` | Field type mapping; `import-types` can additionally specify import types for the VO. If a type cannot be matched, quickvo prints a hint in the log — use it to supplement type-mapping |

> Since quickvo 5.0.1, entity supports **lombok** as well as custom api-doc frameworks.

## 3. Generated Classes and Annotations

Each table generates **two classes, AbstractVO + VO**, where the VO extends AbstractVO. sqltoy parses the VO through annotations:

- `@Entity(tableName="sqltoy_dict_detail", pk_constraint="PRIMARY")`: corresponds to the concrete table (`org.sagacity.sqltoy.config.annotation.Entity`);
- `@SqlToyEntity`: marks the precise anchor when resolving a VO — after finding `@SqlToyEntity`, sqltoy looks at its parent class to locate the class that actually maps to the table, then collects `@Id` and `@Column` to build the complete object-to-table mapping;
- `@Id`, `@Column`: primary key and column mapping.

quickvo also writes the database table/column comments into the VO, which makes it easier to read and maintain.

> [!WARNING]
> Do not modify anything inside the "marked section" of a VO (it will be overwritten on regeneration). To add extra properties or get/set methods, place them **outside** that section.

## 4. Key Caveats

**Duplicated or mixed-up fields on multi-instance databases**: when tables with the same name (e.g. `SYS_STAFF_INFO`) exist in multiple instance databases, the generated VO may contain duplicated fields or fields that belong to another database.

Solution: **configure the datasource's `schema` or `catalog` correctly** (configuring `schema` is usually enough). Both table metadata and column metadata retrieval depend on this setting; a wrong value causes quickvo to fetch tables/columns that do not belong to the current database.

## 5. Strict VO (DTO) / POJO (entity) Layering

For medium and large projects we recommend strictly separating the VO/DTO used for external interaction from the persistence-layer POJO, generating them into different packages via quickvo configuration, and converting between VO and POJO in the business layer (see [Utility classes: DTO ↔ POJO conversion](../tools/utils.md)).

- Layered example project: https://github.com/sagframe/sqltoy-strict
